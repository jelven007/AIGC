# 单机ECS 100人容量验收

日期：2026-10-31。入口：`https://ecs.example.com`。项目：`shopro-ecs`。最终100人容量、限流恢复、清理与26容器备份恢复全部通过，原公网实例已恢复运行。

## 业务与容量范围

100个独立普通账号分别真实登录，使用本人JWT开展商品读写、任务列表、资料/余额/作品查询、模型目录和素材管理。所有请求经过统一HTTPS网关，保留原Auth、RLS、套餐、配额和幂等规则。管理员密钥仅用于创建/清理临时账号及观测汇总。

同时上传100份精确1MiB、10秒带音频MP4素材，各自创建工程、提交本地720p/30fps字幕成片任务，并重复原请求键验证只生成一个任务。持久队列由16个FFmpeg副本处理；成片由本人获取限时签名后真实下载，核验MP4头、大小、摘要、时长、分辨率及尝试次数。按任务实际`credit_cost`核对余额变化和消费流水；现有本地合成成本为0，余额及扣费流水必须不变。

容量负载在ECS本机通过公网规范HTTPS地址和严格CA/IP SAN测量；公网macOS客户端单独验证默认管理员、关键页面、旧作品及100条Realtime。内测延迟不代表各地区公网带宽。

## 实际改造

## 压测发现与修复

1. 原配置100人同时登录仅3人成功，9个HTTP500、88个HTTP504，P95约10.66秒。Auth默认最大池无界，耗尽原数据库100连接，原0.5CPU密码校验也拖慢登录。提升资源并限制Auth20、数据库240后，同批账号100人同时登录全部成功。
2. 查询100个UUID的PostgREST回显响应头超过Nginx默认4KiB，产生HTTP502。REST专用响应头缓冲提升至16KiB，原批量观测复验成功。
3. 仅设置Auth最大池20、保留默认空闲池0，持续负载反复建立TCP连接，最终出现`cannot assign requested address`、Auth500及业务401。对应Auth2.197.0源码证实固定策略将`MaxIdlePoolSize=0`应用到Go连接池。配置最大/空闲池均20并核验启动日志，随后重新进行五分钟全链路压测。
4. 验收脚本曾错误使用不存在的`updated_at`及假定本地合成必须收费。按原表`completed_at`及任务实际`credit_cost`修正；保留失败回执，用`burst-check`读取原任务，避免重新提交。
5. 更高频率负载曾在45秒约13391请求时出现502/503；网关短连接TIME_WAIT观测达13109。Auth/REST/Storage/Edge改用HTTP/1.1和有界keepalive、Nginx运行线程由auto改为2、nofile8192，并对普通Edge凭据设5请求/秒、突发20。连接复用后的高频阶段TIME_WAIT观测降至84。后台执行器保留独立授权和数据库配额，OPTIONS不消耗限流额度，转发失败不自动重试POST。超量后的版本冲突通过读取本人最新商品版本恢复。
