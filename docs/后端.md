## 1. 已有业务后端

已提交主链路包括用户 Auth/RLS、支付验签/权益事务、逐笔积分、服务端视频队列、不可变模型配置、真实同步文本/图片/音频、MCP JWT。当前官方环境只到 00031 与旧三函数，完整最新版尚未发布。架构/接口以 [TECHNICAL_ARCHITECTURE](TECHNICAL_ARCHITECTURE.md)、[API_AND_DATA](API_AND_DATA.md) 为准。

## 2. 后台需求范围与权限

| 模块 | 后续需求 | 接入边界 |
| --- | --- | --- |
| 用户/套餐 | 本人/跨用户受控查询、账号支持 | 不由客户端 header 或 profiles.role 直接授予管理写权限 |
| 模型 | 现有模型设置页、配置与权限审计 | Auth app_metadata + 数据库授权；不回传 Key/密文 |
| 视频/生产任务 | 查询队列、未知核对、旧版本绑定 | 共用现有事务/RPC；不直接改状态、退款金额或上游 ID |
| 财务 | 支付/权益/积分差异、现金退款审批 | 收款原子事务；遗留 cash refund 未完成，需要独立授权/额度/回收 |
| 运营/质量 | 真实任务质量、供应商成本、用户反馈 | 模拟选品/数据页面不能作为实际指标 |
| 工单/审计 | 证据、责任、处置/复核、审计导出 | 最小权限、敏感字段脱敏、可追踪操作 |

运营/客服/财务/运维是流程职责，完整后台 RBAC 尚未实现。优先只读工作台与异常证据；关键写必须独立受控身份/最小授权与审计，按实际资金风险决定复核流程。

## 3. 推荐方案与数据契约

先使用现有 Supabase 服务端 API/RPC，新增管理 API 作为受控边界，不为后台复制第二套积分/订单/任务状态机。若后续引入独立服务，明确 Auth 验证、service_role 管理、事务边界、迁移和部署成本，不能仅将前端换 URL 称为后端迁移。

管理列表统一分页/排序白名单/过滤、UTC 时间和错误分类；金额使用数据库 numeric 与渠道最小单位，积分使用整数。任务关联 request_key/job/project/charge/config_version，订单关联渠道交易与权益快照。只读统计记录分母/窗口与真实数据源，避免客户端聚合模拟 KPI。

对于现金退款新增申请、额度预占、渠道编号、未知查询、重复并发幂等、权益回收和审计事务；不得复用“客户端金额退款”逻辑。详见 [支付方案](plan/支付.md)。

## 4. 分阶段开发

P0：升级当前后端与模型配置，统一财务管理身份，后台仅提供核对所需查询；保证资金/任务主链路不被新 UI 旁路。

P1：只读用户/任务/订单/成本、工单与审计；接入运行监控，补真实管理授权与越权测试。

P2：受控核对操作、现金退款闭环与审批；私有素材/生产任务按独立已验证契约接入。批量/渲染/发布/metrics 需要真实执行器、持续调度、状态和账单，表结构存在不算完成。

## 5. 接受与运行

双用户/多角色越权、并发退款/核对、重复请求、旧周期、关键写审计、异常恢复与真实渠道/任务均需用例；上线前明确管理员来源、备份/恢复和操作负责人。开发规范见 [DEVELOPMENT_GUIDE](DEVELOPMENT_GUIDE.md)，测试见 [TEST_PLAN](TEST_PLAN.md)，日常责任见 [OPERATIONS_GUIDE](OPERATIONS_GUIDE.md)，运行见 [RUNBOOK](RUNBOOK.md)。
