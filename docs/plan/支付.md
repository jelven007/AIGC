## 1. 范围与资金边界

当前收款链路为“已登录用户选套餐 → 服务端读取价格并创建订单/权益快照 → 渠道支付 → 服务端验签和核对 → 数据库原子发放权益”。前端金额、页面返回、二维码展示和截图不能证明支付成功。

视频/图片/媒体/知识/分析/情报/翻译预占应用积分，确定失败按原charge返还。注册20一次，新邀请验证后双方50唯一流水，旧邀请不补发；活动按实际资格/UTC日/原UUID。本人get_my_credits权威快照，读失败不伪零/降级，到期保留积分。文本辅助暂免费；图片/封面/编辑默认10、媒体2/2/10/10/10，实际配置为准。

## 2. 实际接口

| 入口 | 方法/身份 | 输入与作用 |
| --- | --- | --- |
| create-payment-order | POST、个人用户 JWT | {plan_id,request_key,expected_amount,expected_credits}；原订单微信 Native 地址，服务端核对精确金额/积分/原快照 |
| wechat-payment-webhook | POST、支付签名；关闭平台 JWT 校验 | 微信原始通知验签、解密、交易核对、原子入账 |
| wechat-trade-ops | POST、个人JWT；本人查单/关闭，可信财务退款 | query/close/refund/refundQuery/receipt；8KB/每分钟30次，原商户/期限/UUID/金额及权益事务 |
| wechat-refund-webhook | POST、微信原文签名/AES-GCM；非平台JWT | 原申请/商户/交易/退款号/总额/退款额和状态绑定，通知/查询只入账一次 |
| alipay-payment-order | POST、个人用户 JWT | {plan_id,request_key,expected_amount,expected_credits}；事务创建/恢复原订单，pageExec POST 表单 |
| alipay-payment-notify | POST、表单/RSA2；关闭平台 JWT 校验 | 不按 JSON 解析，核对 app/卖家/金额/订单/交易，再入账 |
| alipay-trade-query | GET、用户 JWT | ?order_no=...；本人订单的服务端交易查询，正确已支付可幂等补偿 |
| alipay-trade-ops | POST、个人JWT/可信财务角色与客户范围 | refund/refundQuery/receipt/close；00047/00048原申请/签名到账/权益事务，真实商户仍待验收 |

## 3. 订单、权益和积分事务

00028收款/积分，00029/31注册与奖励，00030/34任务原流水/版本，00047/48现金退款与预算，00050原收银请求，00052微信交易/两渠道权益，00056/57团队预算/锁序与现金成本，00060/61验证奖励/本人权益，00062图片编辑共用原流水。新库排除演示18/19，已有库只应用核对后缺失迁移。

| 数据/接口 | 实际责任 |
| --- | --- |
| orders.plan_snapshot | 创建时冻结套餐 ID/名称/积分/等级；后续改套餐不改变原订单权益 |
| provider_trade_no/pay_channel | 渠道交易唯一性与对应关系，不能挪用其他订单交易 |
| entitlement_granted_at | 权益已发放记录；单独事件落库不能替代该证据 |
| alipay_notify_events | 通知审计/去重；事件已存在仍可重试未完成入账 |
| finalize_paid_order | 按账户→订单锁序核对原渠道/交易/金额/快照，套餐/流水/paid同事务，重复already_processed |
| deduct_credits/refund_credit_charge | 原扣费 ID 与 original_charge_id 关联，退款最多一次；跨计费周期不抹掉新周期用量 |
| credit_logs/audit_logs | 财务台账及操作证据；不通过覆盖余额修复流水 |

关键财务 RPC 仅服务端执行；普通用户无法自行发放积分或按金额退款。服务端同步 AI Action 失败使用原扣费 ID 补偿；视频必须经终态证据与事务状态处理，不能绕过队列直接调用通用退款。

## 4. 验签与渠道配置

微信 v3 核对原始正文、时间戳、序列号、签名，使用支付平台公钥与 API v3 Key 解密；核对 merchant/app、CNY、订单总金额与成功交易状态，不把优惠后实付额当订单总额。

微信服务端配置 MERCHANT_ID、MERCHANT_APP_ID、MCH_CERT_SERIAL_NO、MCH_PRIVATE_KEY、MCH_API_V3_KEY、WECHAT_PAY_PUBLIC_KEY_ID、WECHAT_PAY_PUBLIC_KEY；支付和退款回调分别为目标后端 /functions/v1/wechat-payment-webhook 与 /functions/v1/wechat-refund-webhook。凭据只进 Edge Secrets，记录证书/公钥有效期与轮换责任；新单保存原商户/应用，换商户不能按新配置处理旧单。

支付宝配置 ALIPAY_APP_ID、ALIPAY_PRIVATE_KEY、ALIPAY_PUBLIC_KEY、ALIPAY_GATEWAY、ALIPAY_NOTIFY_URL、ALIPAY_SITE_URL，正式收款同时核对 ALIPAY_SELLER_ID/ALIPAY_SELLER_EMAIL。私钥格式遵循 [alipay.ts](../../supabase/functions/_shared/alipay.ts)；当前卖家字段/notify_url 允许为空是开发兼容，正式上线不得省略验收。

仅 TRADE_SUCCESS/TRADE_FINISHED 的有效收款通知入账；退款事件不当作新收款。通知成功回执必须在入账事务完成之后；入账失败返回失败让渠道重试。商户资质、网站域名、回调 HTTPS、沙箱/正式网关要独立核验，不沿用第三方演示地址。

## 5. 退款现状与后续要求

应用积分：明确失败按原扣费返还，重复退款不重复加积分。unknown 仍保留预占，需核对原供应商账号受理后决策；超时不作为未受理证据。

两渠道现金退款已本地交付可信财务/客户范围、原UUID/金额原因、并发预占、查询租约/限次、签名到账与比例权益回收/累计/欠额/审计同事务。PROCESSING/ABNORMAL/unknown保留预占，SUCCESS才回收，CLOSED结案未到账；调度只查原编号，不新出账。微信13PG及原现金16PG、协议/开发和压缩UI通过，真实商户/历史账/到账待验收；企业统一账套和自动发票仍待开发。

财务从原订单选择渠道与原申请恢复，旧商户或异常到账在渠道管理面核对，记录原证据/权益差异，不直接改余额。持久告警记录渠道成功未结算、退款/交易待核对和缺成本，外部通知及目标运行需另验收。

## 供应商现金与预算

供应商现金账本绑定原视频/生产/同步调用及配置版本，账单号应区分供应商/账号，账单行唯一，币种最小单位与原件SHA-256，有凭证零成本可登记，未核对保持缺失。冲销只追加原entry/币种/完整金额，最多一次，不改变积分；自动账单连接器未交付。

00063/64记录每次文本/Reader主备尝试的原request/配置/供应商ID/usage，运营用原attempt ID登记现金；unknown和未核对金额保持未知，不能从token或积分推算已发生现金。脚本无效/明确拒绝只按原流水一次补偿，存在未知或成功尝试时禁止按拒绝补偿。00065保留资金两份执行机会，不自动新发现金退款。

个人/团队UTC日积分预算统一扣费事务执行，原charge固定创建时归因，退款不抹除预算。多镜头整批固定镜头数×视频+配音+可选字幕预占，后续阶段复用原价/版本/流水。情报计划逐次扣费、确认1–30次总上限；积分预算不能替代供应商现金额度。

## 6. 对账、故障与验收

每日对账：渠道成功交易 ↔ 本地 orders ↔ entitlement_granted_at/套餐 ↔ credit_logs。再比供应商任务用量 ↔ video_jobs/原扣费/退款。分别列出成功未入账、交易/金额不匹配、未知退款、旧 paid 无权益证据和有扣费无终态任务。

通知已落库但权益失败：修复根因后让同一事件重试 finalize_paid_order，不新建订单或加一次积分。支付回跳未到账：服务端查询而非前端认定。旧订单缺快照/权益证据：先人工核对，不把已有 paid 当作可再次发放条件。

本地验收入口为 npm run test:finance、npm run test:payments、npm run test:cash、npm run test:checkout、npm run test:wechat；覆盖金额/渠道/交易错误、原UUID并发、改价与权益快照、一次入账、退款/故障回滚与周期边界。真实沙箱还需正常付款、伪造签名、重复通知、延迟/丢失通知、套餐改价、用户越权与恢复，现金退款必须核对真实到账与权益。
