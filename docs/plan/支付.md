# 支付、权益与积分方案

00041 [素材分析](../ITERATION_12_GROUNDED_ANALYSIS.md)默认预占6积分，确认价格及3任务配额在账户锁内检查，原请求幂等；模型超时unknown保留消费，明确失败原退款一次。ASR/文本证据逐段保存，结案恢复不重复供应商POST。当前高光render免积分；现金退款权益事务仍未覆盖，不能混同应用积分补偿。

更新：2026-10-21，源码基线 `ce90bfe`。本文替代旧支付示例，以实际接口与数据库事务为准。当前云端仅部署旧三函数，支付商户/回调/沙箱尚未验收。环境见 [当前状态](../CURRENT_STATE.md)。

## 1. 范围与资金边界

当前收款链路为“已登录用户选套餐 → 服务端读取价格并创建订单/权益快照 → 渠道支付 → 服务端验签和核对 → 数据库原子发放权益”。前端金额、页面返回、二维码展示和截图不能证明支付成功。

视频创建预占的是应用积分，成功结算、明确失败关联原扣费释放，不是现金退款。注册赠分默认 20，视频默认 10；定价来自配置，积分没有固定货币兑换承诺。同步工作台文本/图片/直接音频暂不收应用积分，供应商仍会收费。

## 2. 实际接口

| 入口 | 方法/身份 | 输入与作用 |
| --- | --- | --- |
| create-payment-order | POST、用户 JWT | {plan_id}；微信 Native 订单/二维码，服务端取套餐金额 |
| wechat-payment-webhook | POST、支付签名；关闭平台 JWT 校验 | 微信原始通知验签、解密、交易核对、原子入账 |
| alipay-payment-order | POST、用户 JWT | {plan_id}；持久化订单，pageExec 生成网站支付 HTML |
| alipay-payment-notify | POST、表单/RSA2；关闭平台 JWT 校验 | 不按 JSON 解析，核对 app/卖家/金额/订单/交易，再入账 |
| alipay-trade-query | GET、用户 JWT | ?order_no=...；本人订单的服务端交易查询，正确已支付可幂等补偿 |
| alipay-trade-ops | POST、遗留 profiles.role 管理权限 | refund/refundQuery/close；**未纳入已验收现金退款闭环** |

支付接口通常返回 {code,message,data}，不是所有业务函数都同一种包裹结构。微信创建返回 order_no/order_id/wechat_pay_url/plan_name/amount；支付宝查询 GET，不能沿用旧 POST 示例。

代码见 [微信创建](../../supabase/functions/create-payment-order/index.ts)、[微信通知](../../supabase/functions/wechat-payment-webhook/index.ts)、[支付宝通知](../../supabase/functions/alipay-payment-notify/index.ts)、[共享入账](../../supabase/functions/_shared/payments.ts)。

## 3. 订单、权益和积分事务

迁移 00026 提供支付宝事件/退款表；00028 收敛支付、积分和权限；00029 奖励事务；00030 视频原子终态；00031 免费计划；00032–00034 增加方舟、ACL、模型版本。新库按序执行，已有库只应用核对后的缺失迁移。

| 数据/接口 | 实际责任 |
| --- | --- |
| orders.plan_snapshot | 创建时冻结套餐 ID/名称/积分/等级；后续改套餐不改变原订单权益 |
| provider_trade_no/pay_channel | 渠道交易唯一性与对应关系，不能挪用其他订单交易 |
| entitlement_granted_at | 权益已发放记录；单独事件落库不能替代该证据 |
| alipay_notify_events | 通知审计/去重；事件已存在仍可重试未完成入账 |
| finalize_paid_order | 锁订单，二次核对渠道/交易/金额与快照，套餐/积分流水/paid 同事务；重复返回 already_processed |
| deduct_credits/refund_credit_charge | 原扣费 ID 与 original_charge_id 关联，退款最多一次；跨计费周期不抹掉新周期用量 |
| credit_logs/audit_logs | 财务台账及操作证据；不通过覆盖余额修复流水 |

关键财务 RPC 仅服务端执行；普通用户无法自行发放积分或按金额退款。服务端同步 AI Action 失败使用原扣费 ID 补偿；视频必须经终态证据与事务状态处理，不能绕过队列直接调用通用退款。

## 4. 验签与渠道配置

微信 v3 核对原始正文、时间戳、序列号、签名，使用支付平台公钥与 API v3 Key 解密；核对 merchant/app、CNY、订单总金额与成功交易状态，不把优惠后实付额当订单总额。

微信服务端配置 MERCHANT_ID、MERCHANT_APP_ID、MCH_CERT_SERIAL_NO、MCH_PRIVATE_KEY、MCH_API_V3_KEY、WECHAT_PAY_PUBLIC_KEY_ID、WECHAT_PAY_PUBLIC_KEY；回调为目标后端 /functions/v1/wechat-payment-webhook。凭据只进 Edge Secrets，记录证书/公钥有效期与轮换责任。

支付宝配置 ALIPAY_APP_ID、ALIPAY_PRIVATE_KEY、ALIPAY_PUBLIC_KEY、ALIPAY_GATEWAY、ALIPAY_NOTIFY_URL、ALIPAY_SITE_URL，正式收款同时核对 ALIPAY_SELLER_ID/ALIPAY_SELLER_EMAIL。私钥格式遵循 [alipay.ts](../../supabase/functions/_shared/alipay.ts)；当前卖家字段/notify_url 允许为空是开发兼容，正式上线不得省略验收。

仅 TRADE_SUCCESS/TRADE_FINISHED 的有效收款通知入账；退款事件不当作新收款。通知成功回执必须在入账事务完成之后；入账失败返回失败让渠道重试。商户资质、网站域名、回调 HTTPS、沙箱/正式网关要独立核验，不沿用第三方演示地址。

## 5. 退款现状与后续要求

应用积分：明确失败按原扣费返还，重复退款不重复加积分。unknown 仍保留预占，需核对原供应商账号受理后决策；超时不作为未受理证据。

现金退款：仓库保留 alipay-trade-ops 和 alipay_refunds，已有退款编号/查询概念；但权限仍使用 profiles.role，不同于模型管理员 Auth 双重授权，订单/退款更新不是完整原子资金与权益回收事务，未进行现金退款回归/商户验收。不能称为生产自动退款，不公开该能力。

要交付现金退款，需新增受控授权、订单锁/退款额度预占、不可变申请编号与金额、请求重试同参数、渠道未知结果查询、并发/重复查询幂等、订单累计退款与权益回收事务、人工审批与审计、与收款/任务的对账及专门故障回归。微信原路现金退款未作为当前交付。

当前争议由财务在商户管理面核对处理，并记录实际交易/退款及应用权益差异；不指导客服调用遗留接口改金额或手工直接改积分余额。

## 6. 对账、故障与验收

每日对账：渠道成功交易 ↔ 本地 orders ↔ entitlement_granted_at/套餐 ↔ credit_logs。再比供应商任务用量 ↔ video_jobs/原扣费/退款。分别列出成功未入账、交易/金额不匹配、未知退款、旧 paid 无权益证据和有扣费无终态任务。

通知已落库但权益失败：修复根因后让同一事件重试 finalize_paid_order，不新建订单或加一次积分。支付回跳未到账：服务端查询而非前端认定。旧订单缺快照/权益证据：先人工核对，不把已有 paid 当作可再次发放条件。

本地验收入口为 npm run test:finance、npm run test:payments；覆盖金额/渠道/交易错误、并发一次入账、故障回滚、逐笔补偿与周期边界。真实沙箱还需正常付款、伪造签名、重复通知、延迟/丢失通知、套餐改价、用户越权与恢复；现金退款另设专项接受条件。
