## O04：独立告警、备份与恢复

正式[生产Compose](../../deploy/production/compose.yaml)增加`operations` profile中的`alert-delivery`，与同一项目的scheduler/maintenance共享`scheduler-alerts`持久卷。不要另起`deploy/video-scheduler/compose.yaml`派发器：它属于另一Compose项目，默认卷也不同，会形成重复派发和无法读取原spool。

从[投递模板](../../deploy/video-scheduler/alert-delivery.example.json)生成普通0600的`RUNTIME_SECRETS_DIR/alert-delivery.json`，使用原目标production-worker URL及容器内两个原spool路径。`relay_secret`独立0600，管理PAT不进入运行容器。通过真实目标接受后，可单独启动发送进程：

```sh
docker compose --env-file deploy/production/runtime.env \
  -f deploy/production/compose.yaml --profile operations \
  up -d --no-build --pull never --no-deps alert-delivery
```

这只启动投递，不启动第二套调度。正式开放前须登记Relay持久接受的原event_id、最终值班接收人、重启同UUID去重及断开业务后端时原spool补送。关闭发送用同配置`stop alert-delivery`，保留卷和未确认事件；不能删除spool来消除告警。

备份继续使用[归档与拉回工具](BACKUP_RECOVERY.md)。调度负责人需将以下顺序安装到**已核验目标的独立调度器**，执行身份仅授予备份所需权限，并保存每步退出码、原备份ID及SHA：

1. 按目标备份窗口冻结对象变更、等待在途上传/删除；执行`backup`。
2. 对该同一归档执行`verify`；失败中止，不上传“最近成功”目录冒充本次。
3. `backup_archive.py upload`核对持久回执；未知保持原对象键重试。
4. 在独立故障域`pull`该回执，并在新空隔离PG/Storage执行`restore`。
5. 核对原UNKNOWN、预占/扣费/退款、历史key_id、媒体实物与告警回执。记录恢复点和完整墙钟时间，再处理恢复点后的真实商户/供应商受理。

备份周期、保留天数、容量、暂停窗口和RPO/RTO须填写后验收。归档密钥与密文分开保管，恢复失败保持目标隔离。代码/本地双PG工具通过不能替代这些正式证据。

## O08：单商品真实试点

准入：原目标全栈接受、准备开放槽位有真实权限、素材使用权、可播放原实物、登记供应商现金上限和停止条件。先选一个商品/一种目标语言/一条成片链路；登记实际参与者，不预设用户数量和成功率。

每次尝试保留：run_id、原任务UUID、账号/团队、商品及输入hash、配置版本、Prompt版本、确认时间、排队/供应商/归档/渲染时间、原输出字节hash、播放/人工复核结果、原attempt及现金凭证。确定失败和UNKNOWN仍计入尝试；未复核接受率为NULL，未知现金单列。

```sh
node scripts/evaluate_ai.mjs --check-dataset
node scripts/evaluate_ai.mjs --results /受控目录/实际结果.jsonl
```

[固定32样本](../ai/evaluation-v1.json)检验相关协议和边界，评估器不发起供应商请求。记录`kind=provider`和人工review；fixture另组，不能用于真实质量结论。实际商品成片的视觉、口型及可播放性须另外复核。成本按同组全部已核对尝试现金/人工接受成片数计算，逐币种呈现。

停止条件：身份/商品事实/私有素材错误，资金账差，原请求恢复失败，无法核对的UNKNOWN超过已登记期限，现金或资源超过已登记上限。停止新提交与新领取，保留原回执处理；没有登记阈值时不扩大试点。

## O09：日常原账与处置队列

使用现有`/operations`可信角色和账号范围；财务、运营、风险、审计分别持权。每天同一UTC截止点登记下表，实际负责人/复核人/响应期限必须补齐。

| 队列 | 查询及核对 | 允许动作 / 结案证据 |
| --- | --- | --- |
| UNKNOWN及submitting | 原UUID、年龄、供应商账号/受理号、原attempt和最后查询 | 查询原请求；真实未受理/确定失败后按原流水补偿，不换UUID重发 |
| 支付与退款 | 原渠道/商户号、订单、原申请、签名终态、权益流水 | 查询原申请；签名成功与原账/权益一致才结案，异常转人工 |
| 个人与团队预算 | 日预算预占、原任务、团队归因、积分扣返、限制版本 | 核对事务和当前范围；不能直接改余额或把积分等同现金 |
| 供应商现金 | 原调用/attempt、配置、供应商账号、币种/最小单位/凭证hash | 追加原账，错误追加冲销；未知不计零，不合并不同币种 |
| 支持与告警 | 原工单/event_id、公开回复/内部备注、接手和最终回执 | 指派、核对、答复、结案；告警接受和人员送达分别记录 |

日报至少列各队列数量/最老年龄、未核对现金、账差、逾期处置和证据链接。自动账单连接器、企业统一付款/审批目前属于O14需求，不以人工登记功能宣称自动化已上线。

## O11：同数据基线与退出条件

每次测量登记机器/架构、镜像ID、源码SHA、样本hash、冷温缓存、并发、原始资源及失败/UNKNOWN分组。先登记预算再比较，HTTP 200或静态包体不是生产体验SLA。

| 边界 | 已有入口 / 必须补的真实证据 |
| --- | --- |
| 浏览器静态闭包 | `node scripts/measure_frontend_bundle.mjs`，180000字节gzip门禁；真实LCP/INP、网络、设备另测 |
| DB | `python3 scripts/measure_database.py --help`核对当前参数，隔离PG同数据测量；真实API权限/连接/锁等待另测 |
| 媒体 | `scripts/measure_media_worker.py`在固定媒体镜像内执行，固定FFmpeg实物/下载/磁盘/RSS；生产长素材分组 |
| 任务/API | 分列领取、排队、查询、归档及供应商等待，核对最老年龄、公平配额和原请求恢复 |

只有重复证据证明领取/锁等待是瓶颈才试通知broker；DB仍为状态和资金权威。知识ANN须同权限/维度/引用/删源数据比较召回、时延和写入成本。任一身份、资金、引用或恢复退化即停止候选。当前没有正式API容量预算，不能宣称已完成生产调优。

## O12–O14：依赖、退出与独立需求

当前固定Node22.23.4、pnpm10.34.5和镜像digest。本轮只新增与现有本地驱动一致的Playwright1.60.0，锁文件只增加它及其依赖；冻结安装通过。安装工具提示ESLint9和Recharts2支持状态变化，core-js构建脚本仍被既有策略禁止；提示本身不证明产品漏洞或必须立即升主版本。

下一次依赖审查逐包记录：官方支持/修复依据、实际使用面、兼容影响、候选版本、冻结安装、类型/lint/包体及对应浏览器验证。没有证据时维持当前版本；主版本升级单独交付，不能借一次安装自动更新整仓库。CI新浏览器job已加入，远端执行状态须另取真实回执。

退出模型先停新任务或切新配置版本；旧任务保留原供应商账号、版本和历史密钥查询。平台退出保留原OAuth快照/发布受理回执，先查原发布，再撤销新授权。平台/基础设施迁移先在隔离目标恢复Auth UUID、原账与Storage，通过接受后才切入口；不靠改URL完成迁移。
