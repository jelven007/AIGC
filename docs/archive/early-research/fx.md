### 2.1 已有基础值得保留

- 当前 `apps/web/src/pages/` 有 43 个 TSX 页面文件；`supabase/functions/` 有 22 个函数目录（不含 `_shared`）；有 26 个 SQL 迁移文件。这些是文件数量，不是可用功能数量。
- 已有路由懒加载、React Error Boundary、响应式组件、草稿保存、作品列表、素材上传、套餐门禁和积分 Realtime 订阅，无须整体重写前端。
- 已有 JWT 校验辅助函数、按用户隔离的 RLS 设计、带行锁的扣费 RPC、退款 RPC，以及错误日志、模型调用和风险事件表。应修正缺口并统一接入，而不是再建立平行体系。
- 已有文本流式输出、多视频供应商适配、TTS/ASR、模板版本字段、缓存、限流及预算雏形。主要不足在于入口分散、契约不一致、异步履约和实际效果校验。
- 支付宝接入已有 SDK 验签、金额匹配、通知事件去重、查单和退款请求记录；微信回调已有解密和时间窗口检查。仍不能把这些局部措施等同于完整的资金闭环。

### 7.1 已确认的缓存序列化问题

源码使用 `JSON.stringify(params, Object.keys(params).sort())`。本次在本地 JavaScript 中复现：两份不同的嵌套商品输入（名称、价格不同），序列化后 action 保留而 product 均变成空对象，输出完全相同。因此问题不是 SHA-256 强度，而是**哈希前的信息已经丢失**。需要先修规范化算法，再考虑命中率优化。

### 7.2 已有“AI 治理”能力仍需闭环

| 已有设计 | 当前执行缺口 | 正确的改进方向 |
| --- | --- | --- |
| 限流、计费、缓存 | 顺序是先扣费再限流/缓存 | 校验和策略判断先执行；收费必须与实际服务结果及约定政策一致 |
| 自动退款 | 无原扣费绑定；部分失败返回 success:false 而不抛异常 | 由任务终态触发幂等补偿，不依赖前端 catch 是否执行 |
| 模型调用台账 | 多个调用路径绕开网关；记录常缺 provider/model，失败计费可能记成 0 | 所有 adapter 统一记录真实调用和独立账本交易 |
| 日预算 | 查询失败放行；读累计与并发消费之间有窗口 | 原子预占、执行结算、失败释放；预算不足时禁止新派发 |

## 8. 建议收敛后的核心功能流程

这是对既有能力的整合目标，不要求一次性更换技术栈。建议继续使用 React/Supabase，在现有数据模型上补业务事务、可恢复任务和必要的媒体 worker。

| 现有流程 | 建议执行顺序 | 必须保存的事实 |
| --- | --- | --- |
| 登录 | 提交手机号 → 服务端发码/频控 → 服务端验证一次性 OTP → 认证服务签发 session → 读取 profile/权益 | 验证会话、失效状态、用户 ID；不保存可预测的登录密码 |
| 单次生成 | 鉴权 → 参数/资源/套餐检查 → 内容审核 → 限流与缓存策略 → 原子创建任务并预占积分 → worker 提交模型 → 查询/回调 → 验证产物 → 结算或补偿 | user/project/job/attempt、幂等键、报价版本、供应商 task ID、产物与账本 ID |
| 批量生成 | 校验整批与报价 → 创建批次和子项 → 并发受控派发 → 逐项完成/失败 → 汇总交付 → 按项结算/退款 | 批次总额、每项消费、暂停/取消请求、成功产物与失败原因 |
| 编辑导出 | 保存版本化时间线 → 校验素材引用/权限 → 媒体渲染 → 校验编码/时长/音轨 → 保存产物 → 允许下载或发布 | 编辑版本、渲染参数、输入素材摘要、输出媒体元数据 |
| 支付到账 | 服务端创建报价快照订单 → 跳转支付 → 通知验签/业务核验 → 原子确认订单并发权益 → 客户端查单 → 对账补偿 | 支付渠道交易号、通知处理态、权益发放唯一键、金额与账本流水 |
| 发布与分析 | 服务端确认账号授权 → 审核最终产物 → 定时/即时发布 worker → 平台真实回执 → 数据同步 → 归因分析 | 平台账号/视频 ID、回执、同步游标、事件时间、数据来源与归因口径 |

状态设计应包含 `pending/queued/running/succeeded/failed/cancel_requested/cancelled/unknown` 等语义，并由服务端定义允许转换。`unknown` 表示上游结果尚不确定，应优先查单与对账，不能简单等同失败后立即退款并重发。

对异步队列按“允许消息重复投递、业务落账幂等”设计；供应商不支持幂等时必须保存尝试记录并先查询结果，不承诺无法保证的外部执行恰好一次。

- 本轮只有分析文档变更，所列业务缺陷仍待修复；工作区原先已有的支付宝代码纳入分析，但不因本报告而被认定为已完成真实支付验收。

## 10. 推荐实施顺序与验收门槛

### 10.1 按依赖分批实施

| 批次 | 重点工作 | 责任侧 | 依赖 | 交付/退出条件 |
| --- | --- | --- | --- | --- |
| 第一批：安全与资金基线 | Q00 手机登录、Q01–Q06 计费/授权/密钥、Q07–Q10 支付/网关/扣费顺序；同时隔离生产演示分支 | 后端主导，前端和 AI 配合 | 核对已部署配置及受影响账号/密钥 | 直接调用不能绕过验证/计费；重复支付/退款无重复账；旧可预测密码与暴露密钥处理完成 |
| 第二批：可重建与真实履约 | 修迁移链、统一 schema/类型、任务 worker、批量消费、后台源码恢复；先打通一个视频供应商完整链路 | 后端、AI、工程治理 | 第一批的认证与账本规则确定 | 干净检出可构建；迁移可重放；关闭浏览器后任务仍交付；失败可补偿 |
| 第三批：编辑、导出、发布闭环 | 真实媒体渲染、多比例转码、OAuth/定时发布、平台回执、素材权限、稳定草稿与团队/API Key 闭环 | 前端、媒体后端、平台接入 | 任务系统、权限与产物协议 | 用户从商品到脚本/视频/编辑/下载或发布能完成全程；没有假成功 |
| 第四批：可信数据与 AI 效果 | 真实数据回流、指标归一、Prompt/模型评测、RAG、缓存预算、A/B、可观测性和体验优化 | AI、数据、前端、运营 | 真实任务与平台事件可追溯 | KPI 有来源，效果可比较，成本可对账，演示样本不参与经营数据 |

不在未确认团队人数、供应商能力和后台源码来源的情况下承诺具体工期。每批可拆成小 PR，但账户、账本、权限与状态机必须保持一致，不能只修前端提示就视为后端问题解决。

### 10.2 建议最先建立的验收用例

| 类别 | 必测场景 | 通过标准 |
| --- | --- | --- |
| 认证 | 错误/过期/重复 OTP；绕过手机号 UI；旧可预测凭据 | 无法获得有效会话；已验证的合法请求可以登录 |
| 权限 | A/B 用户交叉访问项目、任务、知识、团队和供应商任务 ID；普通用户改余额和流水 | 每个越权请求均拒绝；用户数据不泄漏，账本不被篡改 |
| 扣费 | 负数/0/空金额、重复点击、直接请求、并发余额不足、缓存命中、429 | 扣费只按服务端规则；重复业务只扣一次；拒绝请求不扣款 |
| 退款 | 无原扣费退款、同任务并发退款、已成功任务退款、11 项以上批次创建失败 | 无凭据不可退；有凭据正确按项退；不受前端任意数额决定 |
| 支付 | 错签名/金额/商户、通知重复、查询与通知并发、发权益中途失败、两笔加油包并发、部分退款 | 非法通知拒绝；合法订单权益最终一致；现金、权益、流水可对平 |
| 异步任务 | 页面关闭、服务重启、上游超时但实际已接单、重复回调、取消与完成竞态 | 可恢复到可信终态；不重复付费生成；未知状态可查单解决 |
| 真实产物 | 剪辑/字幕/音轨/滤镜/比例各变化一次；供应商返回空 URL | 产物体现编辑参数；空/无效媒体不标成功 |
| 发布与数据 | 断网、授权过期、计划时区、平台失败、重复数据事件、真实数据为空 | 无假成功；重试可恢复；无数据如实为空；不生成随机经营指标 |
| AI 质量 | 结构异常、文本中错误商品信息、审核 string false、中文知识检索、嵌套参数缓存差异 | 异常可拦截或修复；引用可信；缓存不误命中；降级来源清楚 |
| 工程恢复 | 空库迁移、旧库升级、干净安装、前端/后台类型检查、生产构建 | 无手工补表依赖；文档与实际版本一致；检查结果可重复 |

### 10.3 迭代后应持续观察的指标

| 维度 | 指标口径 | 初期使用方式 |
| --- | --- | --- |
| 履约 | 有效成品完成任务数 / 已受理真实任务数；另列用户取消和演示任务 | 按入口、模型、任务类型分组，先建立真实基线 |
| 延迟 | 创建受理时延、排队时长、生成时长、端到端 p50/p95 | 找出卡在排队、模型还是产物保存，不给模拟进度当性能 |
| 资金与权益 | 重复入账数、重复退款数、支付成功但权益待补偿数、账实差额 | 重复落账与不明差额目标为 0；补偿中的订单单列告警 |
| AI 可用性 | schema 有效率、人工可直接使用率、事实错误率、审核待处理量 | 用固定样例集比较版本，不依赖模型自评分 |
| 成本 | 每个成功交付的上游成本、重试成本、缓存节省、售卖积分与上游支出 | 按实际使用量记录；未记录供应商成本时不宣称毛利 |
| 数据可信度 | 有原始平台回执的指标占比、同步延迟、重复事件数 | 真实/预测/演示分别统计，数据无来源时不得混入经营 KPI |

## 11. 结论

本项目已具备较广的视频生成平台页面覆盖和基础数据/模型接入。现阶段最有价值的完善方向是：**先修账号与资金边界，再把生成、编辑、导出、发布和数据回流变成可恢复、可验证的真实流程，最后优化 AI 质量和用户体验。**

优先投入应集中在现有业务的真实性和可靠性，而非增加新的菜单或模型名称。完成上述基线后，已有页面和服务才能形成可验收、可运营的产品闭环。
